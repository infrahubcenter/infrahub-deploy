# Database Architecture

This document describes the PostgreSQL schema introduced in Step 2. It
covers entity relationships, the resource/authorization model, and the
credential, monitoring, operation, and audit sub-systems. It does not cover
authentication, authorization *enforcement*, or discovery/execution logic —
those are later steps; this schema is designed so they can be added without
restructuring what's here.

The schema lives in `backend/migrations/` (11 numbered goose migrations) and
the queries that read/write it are generated by sqlc from
`backend/sql/queries/` into `backend/internal/database/generated/`.

> **Note (Step 12):** the `databases` table described below is this
> original Step 2 placeholder — a top-level resource row (like `vms`/
> `object_storages`) intended for a future, independent database-resource
> model. Step 12's actual database discovery/monitoring feature
> introduced a separate `database_instances` table (migration `021`,
> modeling a database as a **child of a VM**, not a top-level resource)
> and deliberately left this original table untouched. See
> [docs/database-monitoring.md](database-monitoring.md) for that schema
> and the reasoning.

## 1. Entity relationships

The core hierarchy — the one every future resource type plugs into — is:

```
                     Project
                        │
              ┌─────────┴─────────┐
              │                   │
           Group             (resources may skip
              │               the group and attach
              │               directly to a project)
              └─────────┬─────────┘
                         │
                     Resource  (VM | DATABASE | OBJECT_STORAGE | ...)
                         │
           ┌─────────────┼─────────────┬──────────────┬──────────────┐
           │             │             │              │              │
          vms        databases   object_storages  credentials  monitoring_
                                                                snapshots
           │
           ├── vm_filesystems
           ├── packages ── package_updates
           ├── os_updates
           ├── docker_images
           └── docker_containers
```

## 2. Resource model

`resources` is the single table every infrastructure item hangs off of:

```sql
resources (
  id, project_id NOT NULL, group_id NULL,
  name, resource_type CHECK IN ('VM','DATABASE','OBJECT_STORAGE'),
  status CHECK IN ('UNKNOWN','ONLINE','OFFLINE','WARNING','ERROR','DISABLED'),
  description, created_at, updated_at, deleted_at
)
```

Adding a new resource type (`KUBERNETES`, `LOAD_BALANCER`, `REDIS`,
`SERVICE`, `CLOUD_RESOURCE`, ...) later means:

1. Add the value to the `resource_type` CHECK constraint.
2. Create one new detail table with a unique `resource_id` foreign key
   (mirroring `vms` / `databases` / `object_storages`).

Nothing about `resources`, `resource_permissions`, `credentials`,
`monitoring_snapshots`, `recommendations`, `operations`, or `audit_logs`
changes — they all key off `resource_id` and are already type-agnostic.

**Why `resources` is soft-deleted (`deleted_at`) rather than hard-deleted:**
`monitoring_snapshots`, `operations`, and `audit_logs` reference
`resource_id`. If a resource row disappeared entirely, that history would
either be orphaned or cascade-deleted along with it — losing exactly the
audit trail the schema is meant to preserve. The application marks
`deleted_at` instead of issuing `DELETE`.

**Data-integrity trigger:** a resource's `group_id`, when set, must belong
to the same `project_id` as the resource (`check_resource_group_project()`
in `004_resources.sql`). This can't be expressed as a plain CHECK
constraint (it spans two tables), so it's enforced with a `BEFORE
INSERT OR UPDATE` trigger instead of leaving it to application discipline.

## 3. Authorization relationship

No resource-type-specific permission tables exist. Three tiers, all
resolvable independently and combined by the (future) authorization layer:

| Tier | Table | Grants access to |
| --- | --- | --- |
| Project | `project_members` | Every resource in the project (subject to lower tiers, if any are later made restrictive) |
| Group | `group_members` | Every resource in that group only |
| Resource | `resource_permissions` (resource_id, user_id, permission_id) | One specific resource, with one specific permission |

`permissions` is a flat catalog (`user.view`, `vm.execute`,
`storage.manage`, ...) shared across all three tiers — `roles` bundle
permissions for the project/group tiers via `user_roles`, while
`resource_permissions` grants a single permission on a single resource
directly, e.g. "user A gets `vm.connect` on `backend-vm-01`" without
touching that VM's project or group membership.

This step only creates these relationships. No middleware reads them yet
(see `internal/middleware` — logging and recovery only).

## 4. Credential architecture

```sql
credentials (
  id, resource_id NOT NULL, credential_type CHECK IN
    ('SSH_PRIVATE_KEY','DATABASE_PASSWORD','S3_SECRET_ACCESS_KEY'),
  encrypted_data bytea NOT NULL, created_at, updated_at
)
```

- One `resources` row can have multiple `credentials` rows (e.g. a
  rotated SSH key kept alongside the old one, or distinct credential
  types for the same resource).
- `encrypted_data` is `bytea` and must **only ever contain ciphertext**.
  This migration creates the column; it does not implement encryption.
  A later step adds an application-layer encrypt-before-insert /
  decrypt-after-select boundary (see the column comment in
  `006_credentials.sql`). No code in this step reads or logs
  `encrypted_data`.
- `vms.username`, `databases.username`, `object_storages.access_key_id`
  are **not** secrets (SSH username, DB username, S3 access key ID are
  identifiers, not credentials) and stay on the detail tables directly.
  The corresponding secret half (private key, DB password, S3 secret
  key) always lives in `credentials`.

## 5. Monitoring architecture

`monitoring_snapshots` holds only metrics common across resource types
(CPU/memory/storage/network + a status). It is intentionally **not** a
catch-all: a resource type with metrics that don't fit this shape (e.g.
active DB connection count) gets its own snapshot table later rather than
widening this one with nullable columns nobody else uses.

`vm_filesystems` is a VM-specific time series (a VM can report multiple
mount points per capture) and lives next to `monitoring_snapshots` for the
same reason `vms` lives next to `resources` — one common table, one
detail table per type where the shape genuinely differs.

Both tables are pure time series: no `updated_at` (rows are never
mutated, only inserted) and no soft-delete (retention/pruning is an
operational concern for a later step, not a schema concern now).

## 6. Operation architecture

`operations` is an admin-requested action (OS update, package update,
Docker operation, database operation, storage operation) with a lifecycle:
`PENDING → APPROVED → RUNNING → SUCCESS | FAILED | CANCELLED`.
`operation_logs` holds its (ordered, append-friendly) output lines,
tagged `STDOUT` / `STDERR` / `SYSTEM`.

**Nothing in this step executes anything.** These tables only model the
request/result/log shape that a later execution engine will populate.

Unlike the resource detail tables, `operations.resource_id` and
`operations.requested_by` are both nullable with `ON DELETE SET NULL`
(not `CASCADE`) — per the retention rule in §7, deleting a resource or a
user must not delete the operation history that references it.
`operation_logs` does cascade from `operations`, since a log line has no
meaning independent of the operation it belongs to (and operations
themselves are expected to be retained, not deleted, in normal use).

## 7. Audit architecture

`audit_logs` records actions across every entity type — user, project,
group, resource, permission grant, and more — not just resources. Because
of that, `resource_id` is a **plain `uuid` column, not a foreign key**: it
may point into `resources`, `users`, `projects`, or `groups` depending on
`action`/`resource_type`, or be `NULL` for actions with no single target
(e.g. `USER_LOGIN`). `audit_logs.user_id` **is** a foreign key (to the
actor), nullable with `ON DELETE SET NULL` so the audit trail survives a
deleted user account.

**Retention rule applied throughout this schema:** `audit_logs`,
`operations`, and `operation_logs` are historical records and must never
disappear because something they reference was removed. Every foreign key
out of those three tables is either `ON DELETE SET NULL` or (for
`operation_logs → operations`) cascades only within the same
aggregate — never `CASCADE` back to a resource or user.

`audit_logs` is append-only by construction, not just convention, via two
triggers (`013_fix_audit_log_append_only.sql`): `BEFORE DELETE` rejects any
row removal outright, and `BEFORE UPDATE` rejects any change to a row's
content, with one narrow exception -- `user_id` transitioning from set to
`NULL` with every other column unchanged, which is exactly what the
`ON DELETE SET NULL` FK action above does when the referenced user is
deleted. (011's original single trigger blocked *all* updates, which also
blocked that FK action itself -- deleting an audited user failed outright.
013 is the fix.) Step 3's `internal/services/audit.go` now writes to this
table on every login/logout/access-grant/access-revoke event.
